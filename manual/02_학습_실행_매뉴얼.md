## 단계 A. (선택) 서버 InfluxDB 이력 받기

합성 데이터만으로도 1회차 학습은 된다(`configs/dataset.yaml` 의 `replay.enabled: false` 그대로). 실데이터를 섞으려면:

서버(네이버 클라우드)는 InfluxDB **조회 전용 창구** `https://smartcubens.duckdns.org/influx` 를 열어 두었다 — 집에서 터널 없이 받을 수 있다.

1. 읽기 전용 토큰을 환경변수로(서버 `.env` 의 `INFLUX_READ_TOKEN` 값 또는 팀이 정한 공개 읽기 토큰. 파일·커밋에 남기지 않는다):
   ```bash
   read -rs INFLUX_READ_TOKEN && export INFLUX_READ_TOKEN     # 붙여넣고 Enter (화면에 안 보임)
   ```
2. **조명을 CUBE001 로 옮긴 날 찾기** (날짜를 모를 때). 넓은 기간의 LED·조도만 받아 날마다 상관을 본다:
   ```bash
   mkdir -p data/raw
   python -m helpai_decide export-influx --start 2026-10-01 --stop $(date +%F) \
       --zone-config configs/light_check.yaml --out data/raw/light_check.csv
   python -m helpai_decide light-check --csv data/raw/light_check.csv
   ```
   출력 예:
   ```
   날짜(KST)       분  LED표준편차    상관  CUBE002.led1분
   2026-10-24    1380     21.3   0.04      1380
   2026-10-25    1384     19.8  -0.02      1201
   2026-10-27    1390     22.0   0.91         0
   …
   제안: 조명이 CUBE001 에 있다고 볼 첫날 = 2026-10-27
   ```
   - **상관**: CUBE001 의 LED 를 바꿀 때 CUBE001 조도가 따라오면 1 에 가깝다(조명이 CUBE001 위). 0 근처면 조명이 다른 곳.
   - **CUBE002.led1분**: CUBE002 가 LED 값을 보고한 분 수. 조명을 떼어 낸 뒤 0 이 되거나 장치가 꺼졌으면 함께 단서가 된다.
   - 상관이 `-` 인 날은 LED 가 거의 안 움직였거나 데이터가 모자라 판단을 건너뛴 날이다.
   - 옮긴 날 당일은 섞여 있으니 **제안 날짜 다음 날부터** 쓰면 안전하다. 제안이 없으면 조명이 조도계를 비추는지 현장에서 확인.
3. 학습용 이력 내려받기 (기본 `--url` 이 위 창구다):
   ```bash
   MOVED=2026-10-28                    # 2 의 제안 날짜 + 1 일 (예)
   python -m helpai_decide export-influx --start $MOVED --stop $(date +%F) \
       --out data/raw/influx_cube001.csv
   ```
   하루 단위로 나눠 받으며 `누적 N 분` 을 찍는다. 결과 CSV 첫 줄 = `time,CUBE001.ads1115_ok,CUBE001.air,CUBE001.fan1,…,CUBE001.water`.
   - ★ **`--start` 는 조명을 CUBE001 로 다시 옮긴 날 이후로.** 그 전 이력은 CUBE001.led1 이 실제 조명이 아니라 LED↔조도 관계가 틀린 데이터다 — 학습을 망친다.
   - 큐브 이름이 클라우드 이전 뒤 바뀌었으면 `configs/replay.yaml` 의 `CUBE001` 을 고친다.
   - 창구가 401 이면 토큰, 404 면 경로(`…/influx` 뒤에 아무것도 붙이지 않는다 — 클라이언트가 `/api/v2/query` 를 붙인다).
   - 창구를 쓸 수 없으면 서버에 SSH 터널: `ssh -N -L 8086:127.0.0.1:8086 <서버 계정>@<서버>` 후 `--url http://127.0.0.1:8086`.
4. `configs/dataset.yaml` → `replay.enabled: true`, `csv:` 에 파일 경로.
   큐브 배치가 바뀌었으면 `configs/replay.yaml` 을 고친다(autoctl 과 같이 큐브 한 대 기준).

> CSV 는 `data/` 아래라 git 에 올라가지 않는다. 다른 PC 에서는 같은 명령으로 다시 받으면 된다.

## 단계별

| # | 명령 | 하는 일 | 확인할 것 | 예상 시간 |
|---|---|---|---|---|
| 0 | `python -m helpai_decide check-env` | 환경 점검 | `결과: 통과` | 수 초 |
| 1 | `python -m helpai_decide download-base --out models/base` | typed-decisions 체크포인트 | `model.safetensors ~800 MB`, `rl_agent_config.json`, `rl_common.py`, `tokenizer/` 목록 | 수 분 |
| 2 | `python -m helpai_decide dataset build --config configs/dataset.yaml --out data/dataset` | 합성(+재생) → train/val/test | `split_train ≈ 16000`, 질문별 정답 분포가 한쪽으로 90 % 넘게 쏠리지 않았는지 | 수십 초 |
| 3 | `python -m helpai_decide dataset check --data data/dataset/train.jsonl` (val·test 도) | 형식 검사 | `통과` | 수 초 |
| 4 | `python -m helpai_decide token-count --tokenizer models/base/tokenizer` | state 토큰 실측 | p95 가 **400 이하**(기반 문맥 1024 에 질문·선택지 몫을 남김) | 수 초 |
| 5 | `python -m helpai_decide train --out runs/$REV/model` | 미세조정 | `TrainConfig: …`, `dry_run → …`, 에폭별 손실이 내려감, `학습 끝 N 분` | **실측** (수십 분~수 시간) |
| 6 | `python -m helpai_decide export-onnx --model-dir runs/$REV/model --out runs/$REV/onnx_fp32` | ONNX fp32 | `max |dlogits|` 가 1e-4 이하(내보내기 스크립트 출력), `ONNX(fp32) → … (~1700 MB)` | 수 분 |
| 7 | `python -m helpai_decide convert --src runs/$REV/onnx_fp32 --out runs/$REV/onnx_int8` | INT8 | `INT8 → … (~450 MB)` | 수 분 |
| 8 | 서버 2 개 띄우고 `predict` ×4 (아래 상자) | fp32·INT8 로 val·test 예측 | `예측 N 건 (실패 0)`, 지연 | 수십 분 |
| 9 | `python -m helpai_decide compare --a runs/$REV/pred_test_fp32.jsonl --b runs/$REV/pred_test_int8.jsonl` | 일치율 | `최상위 답 일치율 최저 ≥ 0.97 — 통과` | 수 초 |
| 10 | `python -m helpai_decide calibrate --preds runs/$REV/pred_val_int8.jsonl --out runs/$REV/calibration.yaml` | 질문별 온도 | 각 질문 `ECE a → b` 에서 b 가 작아짐 | 수 초 |
| 11 | `python -m helpai_decide evaluate --preds runs/$REV/pred_test_int8.jsonl --calibration runs/$REV/calibration.yaml --out runs/$REV/eval_report.json` | 평가 | 질문별 `합격/불합격` 표 | 수 초 |
| 12 | `bundle make … && bundle verify bundles/$REV` (pipeline.sh 12 단계 참고) | 묶음 | `통과`, `bundles/$REV.tar` | 수 초 |
| 13 | (pipeline.sh) | 작은 보고서 → `reports/$REV/` | | |

**8 단계 직접 할 때**

```bash
# 터미널 1, 2 — 집 PC 에서 젯슨과 같은 서버 코드로
LAYA_MODEL_DIR=$PWD/runs/$REV/onnx_fp32 LAYA_ALLOW_UNBUNDLED=1 LAYA_THREADS=8 PORT=8101 HOST=127.0.0.1 node edge/server.mjs
LAYA_MODEL_DIR=$PWD/runs/$REV/onnx_int8 LAYA_ALLOW_UNBUNDLED=1 LAYA_THREADS=8 PORT=8102 HOST=127.0.0.1 node edge/server.mjs
# 터미널 3
for s in val test; do
  python -m helpai_decide predict --endpoint http://127.0.0.1:8101 --data data/dataset/$s.jsonl --out runs/$REV/pred_${s}_fp32.jsonl
  python -m helpai_decide predict --endpoint http://127.0.0.1:8102 --data data/dataset/$s.jsonl --out runs/$REV/pred_${s}_int8.jsonl
done
```
서버가 `적재 … from …` 을 찍어야 준비된 것이다. `curl -s 127.0.0.1:8102/health` 로도 확인.

> 학습 직후 PyTorch 원본으로 빨리 보고 싶으면: `python -m helpai_decide predict --model-dir runs/$REV/model --data data/dataset/test.jsonl --out runs/$REV/pred_test_torch.jsonl --limit 300`
> (laya 파이썬 API 이름이 판마다 달라 실패할 수 있다 — 그때는 8 단계 서버 경로가 기준이다.)

## 결과 판단

| 상황 | 할 일 |
|---|---|
| 11 단계 전 질문 합격 | 그대로 젯슨으로 (매뉴얼 03) |
| 일부 질문 불합격 | 그래도 묶음을 만든다 — 젯슨에서 그 질문만 shadow. `eval_report.json` 의 `confusion` 으로 어디서 틀리는지 보고 다음 회차에 데이터 보강(합성 seed 추가, 해당 경계 `edge_frac` 증가) |
| 9 단계 일치율 < 0.97 | INT8 대신 FP16: `convert --precision fp16 --out runs/$REV/onnx_fp16` → 8~12 단계를 fp16 으로, `bundle make --precision fp16` |
| 손실이 안 내려감 / 정확도가 최빈값 찍기 수준 | `configs/training.yaml` `loss: soft-ce` 로 한 번 비교. 학습률 절반. 매뉴얼 04 |
| CUDA out of memory | `micro_batch: 4` → 그래도면 `gradient_checkpointing: true` |
